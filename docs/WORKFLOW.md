# Простой рабочий процесс

## Один источник задач

[TASKS.md](../TASKS.md) хранит текущий этап, ближайшую задачу, чекбоксы и короткие результаты. Не нужны GitHub Issues, PR, отдельный трекер, обязательные роли или копия задач в JSON. Продуктовые и архитектурные решения находятся в своих документах и связываются с задачей по ID.

Обычно одна задача в работе. Для неё достаточно цели, нескольких критериев готовности и заметки о результате. Не составлять отдельный большой план для небольшого изменения.

## Цикл реализации

1. Проверить `git status --short`, прочитать задачу и относящиеся к ней требования. Отметить её ID в строке «В работе».
2. Выполнить небольшой законченный набор изменений. Новый существенный выбор записать в архитектуре; не расширять MVP незаметно.
3. Запустить целевые проверки после осмысленного набора изменений. Перед завершением MVP выполнить ручную приёмку. Не запускать полный набор после каждой правки текста.
4. В задаче записать результат, фактическую команду/ручную проверку и ограничения. Поставить `[x]` только после выполнения критериев. Частичный результат оставить `[ ]` с пояснением.
5. Просмотреть diff, сделать локальный коммит, обновить ближайший шаг. Коротко сообщить владельцу, что работает и что ещё не проверено.

Если требуется решение владельца, сформулировать конкретную развилку; независимую работу продолжать. Не просить повторное разрешение на обычные действия в уже согласованном этапе. Запрос «подготовить документацию» сам по себе не разрешает начать реализацию.

## Локальный Git

Рабочая ветка — `main`. Для крупных экспериментов допустима короткая локальная ветка `task/HT-03-hover`; ветки и merge-коммиты не обязательны. По запросу владельца 2026-10-17 создан публичный origin [progmonster/chrome-hovertrans](https://github.com/progmonster/chrome-hovertrans), текущая история отправлена в main. Последующие push выполнять по запросу владельца; публикация в Chrome Web Store требует отдельного запроса.

В рамках согласованного этапа разработки разрешены небольшие локальные коммиты. Не включать чужие изменения; добавлять конкретные пути. Если Git не настроен, запросить данные автора, не выдумывать и не менять глобальный конфиг.

```sh
git status --short
git diff --check
git diff
git add TASKS.md docs/PRODUCT.md
git diff --cached
git commit -m "docs: clarify hover activation"
```

Сообщения: краткий повелительный заголовок, предпочтительно `docs:`, `feat:`, `fix:`, `test:`, `chore:`; например `feat: show translation popup`. Это выбранная конвенция нового проекта, а не вывод из старой истории.

Не использовать `reset --hard`, очистку неизвестных файлов, переписывание истории и удаление пользовательских данных как обычный шаг. Исправления по умолчанию — следующим коммитом.

## Готовность задачи

Критерии выполнены, относящиеся к ним проверки пройдены, документация актуальна, остающиеся ограничения названы. Коммит подтверждает сохранение результата; он не подтверждает ручную приёмку. Завершение подготовки документов не означает готовность расширения.
